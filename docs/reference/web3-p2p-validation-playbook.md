# OpenClaw P2P 协同算力验证手册

> **Status**: Execution playbook  
> **Updated**: 2026-03-09  
> **Goal**: 帮助另一位 AI 伙伴或工程执行者，以最小风险验证 `OpenClaw` 的 P2P 协同算力方向，而不是一开始就陷入过度设计。

## 1. 验证目标

本手册只服务一个目标：

> **尽快证明 `OpenClaw` 能把“可信圈设备 + 市场化算力”组织成一个可发现、可租用、可计量、可结算、可审计的协同算力闭环。**

不是所有能力都要一次到位。第一阶段要验证的是：

- 能不能发现节点
- 能不能区分节点类型
- 能不能建立可信圈策略
- 能不能把任务发给合适节点
- 能不能形成账本、结算与审计闭环

## 2. 成功标准

### 2.1 MVP 成功标准

若满足以下条件，即认为 MVP 成立：

1. 至少有两类节点：
   - 一个 `算力池节点`
   - 一个 `个人电脑子节点`
2. 节点可以被 `OpenClaw` 发现并区分角色
3. 资源可以发布与列出
4. 可以创建租约或任务
5. 至少一种真实工作负载可以被路由到远端节点执行
6. 账本、结算或奖励至少完成一个闭环
7. 所有对外输出保持脱敏，不泄露 token/endpoint/path

### 2.2 不是 MVP 必需项

以下能力不属于第一阶段阻塞项：

- 公网匿名节点大规模接入
- 通用逐层协同解码
- 完整信誉系统
- 复杂代币经济
- 极低延迟实时主脑推理

## 3. 推荐验证顺序

### Phase 0：事实核对与边界冻结

#### 目标

先核对仓库现有能力，冻结当前可复用边界，避免“假设驱动开发”。

#### 要确认的事实

- `web3.*` / `web3.market.*` 是唯一对外入口
- `market-core` 是权威状态机
- `web3.index.*`、`web3.monitor.*`、`web3.market.task.*`、`web3.market.privacy.*`、`web3.reward.*` 等公共面已存在
- 输出不得泄露 `accessToken`、endpoint、真实路径

#### Phase 0 产物

- 一份节点角色表
- 一份工作负载分级表
- 一份“当前事实 vs 目标态”清单

#### 通过标准

- 团队对现状与下一阶段边界达成共识
- 不再把“执行引擎能力”和“市场/治理能力”混为一谈

### Phase 0.5：可信执行路径分流

#### 目标

在开始实现前，先决定“哪一类信任问题用哪一类技术解”。

#### 推荐分流

##### A. 默认基线：常规加密与最小披露

这部分直接视为必选项，而不是实验项：

- TLS / 存储加密 / 短期凭证
- 输出脱敏
- endpoint / token / path 不外露
- 任务输入按最小披露原则出圈

##### B. 第一优先工程路线：机密虚拟机 / 机密 GPU / 远程证明

这条线最适合优先验证，因为它已经有明确工程抓手：

- `Azure Confidential Computing` 已把 **data in use** 保护产品化；
- `Intel TDX` / `AMD SEV-SNP` 提供硬件隔离的机密 VM；
- `NVIDIA Secure AI` 已支持带 `TEE + attestation` 的机密 AI 运行形态。

推荐把它用于：

- 算力池节点
- 组织内稳定节点
- 高敏感、高价值任务
- 需要更强合规与审计口径的执行面

##### C. 暂不作为 MVP 主路径：FHE / MPC / ZK

这类路线应继续跟踪，但默认不把它们放进 MVP 主闭环：

- `FHE`：可用于强隐私但低吞吐场景，性能代价仍重；
- `MPC`：可做私有协作计算，但系统复杂度与时延代价高；
- `ZK`：适合做“证明某事被正确执行”的补充层，不适合一开始承载通用在线推理主链路。

#### Phase 0.5 验收标准

- 至少明确一类任务必须跑在 `TEE` 节点上
- 至少明确一类任务只允许留在可信圈普通节点内
- 不再把 `FHE/MPC/ZK` 误当作第一阶段的通用默认答案

## 4. MVP：可信圈内资源协调闭环

### 4.1 目标

在一个**小规模可信圈**中，验证“资源发现 → 任务/租约 → 执行 → 账本/结算/审计”的最小闭环。

### 4.2 推荐节点构成

- **节点 A**：OpenClaw 主控节点（Gateway + `web3-core` + `market-core`）
- **节点 B**：算力池节点（可接外部执行器，例如 `vLLM` 或模拟 Provider）
- **节点 C**：个人电脑子节点（Mac/PC，执行轻量任务或本地模型调用）

### 4.3 推荐工作负载

优先选以下之一：

- 批量摘要
- embedding / rerank
- 离线分类
- 异步工具工作流
- 受控的远端 LLM 调用

不要一开始就选：

- 逐 token 实时对话主脑
- 跨公网分层协同解码

### 4.4 推荐动作序列

1. 建立一个最小可信圈
2. 发布两种资源：
   - 稳定池节点资源
   - 个人子节点资源
3. 通过 `web3.index.*` 或现有发现面确认两者可见
4. 发起一次租约或任务
5. 将任务路由到合适节点执行
6. 记录账本与执行结果
7. 形成一次结算或奖励更新
8. 通过监控/审计视图验证结果可观察

### 4.5 MVP 验收标准

- 同一工作负载可基于策略路由到不同类型节点
- 节点掉线或不可用时，系统能给出明确降级或失败原因
- 账本/结算记录可查询
- 状态输出为脱敏摘要，而不是底层连接细节

## 5. Phase 1：可信组圈与节点策略化

### 5.1 目标

把“能跑通”升级为“能按策略运行”。

### 5.2 本阶段新增验证点

- 组圈策略：
  - 哪些节点能加入
  - 哪些任务可出圈
  - 哪些任务只允许本地或池节点执行
- 节点分类策略：
  - 池节点优先级
  - 个人节点优先级
  - 回退顺序
- 健康与监控：
  - 节点在线率
  - 最近失败率
  - 任务完成时长
- 基础激励：
  - 节点完成任务后是否能形成奖励或收益记录

### 5.3 推荐新增工作负载

- 夜间批量任务
- 可信圈内私有知识处理
- 轻量多节点分发任务

### 5.4 Phase 1 验收标准

- 至少存在一条“池节点失败 → 个人节点补峰”或反向回退逻辑
- 同一个可信圈内可对不同任务类别应用不同调度策略
- 监控面能分辨：
  - 哪类节点更稳
  - 哪类任务更适合个人节点
- 奖励或对账口径能体现不同供给的贡献差异

## 6. Phase 2：混合供给网络与更强工作负载分级

### 6.1 目标

把 `OpenClaw` 从“小圈闭环”推到“混合供给网络”。

### 6.2 重点验证

- 同时存在：
  - 本地强节点
  - 个人设备子节点
  - 市场化池节点
  - 必要时的云回退节点
- 工作负载按级别路由：
  - 实时任务
  - 异步任务
  - 批处理任务
- 成本与延迟之间的策略切换
- 更完整的收益、奖励、争议与回放链路

### 6.3 推荐验收标准

- 系统能在多个供给层之间切换，而非硬编码单一路径
- 对同一类任务，至少能比较两种供给选择的代价与结果
- 当个人节点不稳定时，不会拖垮整个任务系统
- 结算与审计口径仍保持统一

## 7. 建议的实现优先级

### P0：马上做

- 统一节点角色模型
- 明确可信圈策略对象
- 选定一类最适合的 MVP 工作负载
- 跑通一条“发现 → 路由 → 执行 → 账本/结算”的闭环

### P1：紧接着做

- 节点健康度与简单排序
- 池节点 / 个人节点调度策略
- 监控面聚合
- 奖励或收益归因

### P2：后续做

- 更复杂的信誉与反滥用
- 更开放的节点准入
- 更细粒度的模型分层协同
- 更丰富的隐私保护与执行证明

## 9. 推荐演示脚本

建议演示不要从“模型分层并行”开始，而是从“可解释闭环”开始：

### Demo A：可信圈任务协作

- 用户发起一个批量任务
- `OpenClaw` 发现两个候选节点
- 根据圈子策略与节点类型选择执行者
- 执行完成后生成账本与结算摘要
- 监控页显示一次成功任务与节点贡献

### Demo B：个人节点补峰

- 主池节点被模拟为繁忙或不可用
- 系统将低优先级异步任务调度到个人电脑子节点
- 结果完成后仍保持统一账本与审计口径

### Demo C：隐私边界证明

- 展示状态、日志或工具输出
- 证明系统未泄露 endpoint、token、真实路径
- 用脱敏摘要完成对账与分享

## 10. 不要先做什么

以下事项很容易把项目拖进高复杂度低产出的区域，建议明确推迟：

- 完全开放公网志愿者网络
- 通用逐层解码框架自研
- 用代币经济替代真实供给质量治理
- 试图让所有任务都跑在个人电脑子节点上
- 过早把“完全免费”当作核心卖点

## 11. 风险清单

| 风险         | 表现                                             | 建议应对                                  |
| ------------ | ------------------------------------------------ | ----------------------------------------- |
| 节点不稳定   | 任务超时、执行失败、状态抖动                     | 优先选择异步任务；保留池节点兜底          |
| 延迟过高     | 用户感知差，交互任务不可用                       | 第一阶段避开实时主脑路径                  |
| 隐私泄露     | 输出暴露 endpoint/token/path，或任务输入过度外流 | 默认最小披露；先在可信圈内验证            |
| 供给质量参差 | 个人节点性能差异大                               | 区分角色，建立基础健康评分                |
| 经济闭环不清 | 执行了但无法对账/结算/奖励                       | 先做一条清晰账本与结算路径                |
| 过度设计     | 过早自研复杂调度器                               | 先复用外部执行面，OpenClaw 聚焦控制与治理 |

## 12. 最终建议

如果你希望这条方向尽快落地，而不是继续停留在“高概念”，最好的执行顺序是：

> **先把可信圈中的任务协调闭环跑通，再逐步逼近更复杂的协同推理场景。**

这既符合 `OpenClaw` 当前能力，也最符合工业级验证的现实节奏。
