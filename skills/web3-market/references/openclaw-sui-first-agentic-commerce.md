# OpenClaw Sui-first Agentic Commerce 选型备忘

## 1. 一句话结论

如果 `OpenClaw` 的 Web3 模块要服务 **AI 个体与 AI 个体之间的高频、原子、可编排交易**，当前最值得优先采用的长期账本方向是：

> **`Sui` 负责对象化权利与结算语义，`EVM` 负责稳定币流动性与外部金融兼容，`TON` 负责分发与轻量支付入口。**

这不是在否定当前 `EVM + TON` 的实现价值，而是在明确下一阶段 `Agentic Commerce` 的最优语义承载层。

## 2. 当前事实 vs 目标态

### 当前 repo 事实

- `EVM` 是当前已实现的默认 Web3 Market 主线。
- `TON` 已经进入统一的双栈支付/回执/结算口径。
- `web3.*` 仍是对外公共入口，`market.*` 仍是内部权威执行层。

### 推荐目标态

- 把 `Sui` 视为 **AI-to-AI 交易语义层**，用于承载 capability、lease、receipt、escrow、reward 等对象。
- 把 `EVM` 视为 **稳定币与外部流动性入口**，用于 treasury、bridge、DeFi 兼容与对外资产接入。
- 把 `TON` 视为 **前台触达与轻量支付入口**，特别是 Telegram/分发场景。

## 3. 为什么优先考虑 Sui

### 3.1 它最贴近“万物皆可交易”的建模方式

`Sui` 的对象模型更适合把下列东西直接当成一等对象：

- 能力访问权
- 时间窗租约
- 服务回执
- 托管支付
- 奖励凭证
- 争议与审计锚点

对于 `OpenClaw`，这比把所有东西都塞进一堆 `mapping` / `account` 结构里更自然。

### 3.2 它更适合 AI 的多步原子商务流

AI 代理经常要完成：

1. 锁定预算
2. 支付或托管
3. 获取访问权
4. 调用能力
5. 写入回执
6. 释放结算或进入争议

`PTB` 很适合表达这类多步、必须全成或全败的动作。

### 3.3 它更适合显式所有权转移

`Capability`、`Lease`、`Receipt`、`Reward` 这类对象天然有“归谁所有、是否可转移、何时过期、是否可撤销”的问题。`Sui` 的对象所有权模型更贴近这类业务语义。

## 4. 为什么不是把别的链放在第一位

### `EVM`

- 优势在于流动性、钱包兼容、稳定币与 DeFi 生态。
- 但它对高频 agent 商务动作的表达更像“在总账本上改余额”，不如 `Sui` 那样贴合对象化权利交易。

### `TON`

- 优势在于 Telegram 分发、轻量支付与前台触达。
- 但异步消息语义不适合作为复杂多步原子交易的第一主账本。

### `Solana`

- 性能很强，是认真可选的第二名。
- 但账户/程序分离、显式账户列表、开发心智更偏“高速执行系统”，不如 `Sui` 对“能力对象 / 权利对象 / 交付对象”的语义自然。

## 5. Sui 的能力边界

### 5.1 它不是以太坊生态

- 不是 `EVM`
- 不是以太坊 `L2`
- 不能直接复用 Solidity / ERC 标准的实现路径

因此不要把“迁移到 Sui”理解成“换个 RPC 地址就行”。

### 5.2 它的快，不代表所有场景都无限快

- **Owned Object** 路径非常适合点对点能力交易。
- **Shared Object** 一旦出现热点争用，复杂度和延迟都会上升。

所以 `OpenClaw` 设计上应避免把所有成交都压到一个共享市场大对象里。

### 5.3 它不是执行引擎

`Sui` 不该承载：

- prompt 明文
- 模型权重
- 推理中间状态
- 大体量交付内容

链上只放：

- hash / pointer / policy anchor
- capability / lease / receipt / escrow / reward
- dispute evidence digest

## 6. 对 OpenClaw 的架构含义

### 6.1 角色分工

- `web3-core`：控制面、发现、监控、身份、对外入口
- `market-core`：权威经济状态机
- `Sui`：对象化交易与结算语义层
- `EVM`：稳定币与外部资产入口
- `TON`：分发与轻量支付入口
- 外部执行器：`vLLM`、`TensorRT-LLM`、`exo`、`llama.cpp` 等

### 6.2 推荐的链上对象五件套

最值得优先建模的是：

1. `Capability`
2. `Lease`
3. `Receipt`
4. `Escrow`
5. `Reward`

其中：

- `Capability` 表达“卖什么”
- `Lease` 表达“谁在什么条件下能用”
- `Receipt` 表达“确实发生过什么”
- `Escrow` 表达“钱怎么锁、何时放、出事怎么办”
- `Reward` 表达“如何激励供给、推荐、治理与运营贡献”

## 7. MVP 顺序建议

不因为换到 `Sui-first` 就改变 `OpenClaw` 的正确工程顺序：

1. 节点发现
2. 节点健康与可用性评估
3. 资源发布与能力描述
4. 租约 / 账本 / 结算 / 奖励闭环
5. 最小可行任务分发或工具调用路由
6. 最后才是更激进的模型逐层协同推理

链只是账本与权利层，不会替代调度、执行、监控和争议治理本身。

## 8. 产品与经济建议

- 第一阶段优先用 **稳定币** 结算业务价值。
- `SUI` 主要承担 gas 与对象操作成本。
- 不要急于发行 `OpenClaw` 自己的代币，除非 staking / slashing / governance 已经是明确刚需。

## 9. 设计规则（给后续 AI/工程师）

- 永远区分 **当前运行时事实** 与 **目标态方向**。
- 不要把 `Sui-first` 写成“当前已经全面迁移完成”。
- 先做 **off-chain discovery / quote / routing**，再把关键权利与结算对象上链。
- 先优化 **Owned Object first** 的点对点路径，再考虑共享市场对象的复杂治理。
- 保持 `web3.*` 对外单入口与 `market.*` 内部权威层分离不变。
