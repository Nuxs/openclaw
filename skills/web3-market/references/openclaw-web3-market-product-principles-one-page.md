# OpenClaw Web3 Market Product Principles (One Page)

## Product definition

> **OpenClaw = Private Steward product surface + Web3 Market accountability substrate.**

We do not sell “the chain.” We do not sell abstract autonomy. We sell **accountable execution**.

## One-sentence promise

> **OpenClaw is a private steward that discovers, buys, verifies, settles, and audits outside digital services _on your behalf_, keeping execution invisible yet governed and accountable through human-in-the-loop consent.**

## The one-page rulebook

### 1. Sell the steward, not the chain

Lead with the user outcome:

- the steward understands intent
- the steward can act safely
- the steward can manage outside services responsibly

Web3 stays underneath as the trust, settlement, and audit substrate.

### 2. Build Consent UIs, not Shopping Malls

The UI is for **audit and consent**, not discovery and manual checkout.

- **Bad (Web2.5 approach)**: A traditional dashboard where a human browses a catalog, selects a model/service, configures a TTL, and clicks "Buy".
- **Good (Agent-Driven approach)**: The Agent realizes it needs external capability, discovers it via API, and surfaces an elegant **Consent Card** in the chat stream ("Your steward requests $2.50 to lease advanced code analysis for 24 hours. [Approve] [Reject]").

Important work should be visible as:

- task thread
- execution timeline
- proof summary
- settlement state
- dispute state

What users trust is not abstract capability. They trust visible closure.

### 3. Governance before openness

No default-open public market.

All networked execution should be shaped by:

- identity
- permissions
- allow/deny policy
- budget limits
- auditability
- redaction

If visibility grows faster than governance, the system becomes theater.

### 4. Heartbeat must be policy-driven

Periodic agent behavior is a product primitive, but it must stay bounded.

Use heartbeat for:

- quote refresh
- delivery polling
- SLA follow-up
- approval reminders
- health monitoring

Do not treat heartbeat as a blind remote-command channel.

### 5. Social legibility beats protocol depth

Users understand:

- threads
- communities
- provider pages
- delivery updates
- reputation backed by evidence

Expose execution through socially legible surfaces, not protocol jargon.

### 6. Skills are the onboarding engine

A network grows when joining feels lightweight.

Default packaging should be:

- provider publishing preset
- agent execution preset
- human-in-the-loop consent preset
- service-specific skill packs

Skills are not only extensions. They are the distribution channel for market-backed execution.

### 7. Proof before prestige

Reputation alone is insufficient.

Every serious service flow should trend toward:

- proof
- acceptance
- settlement
- reconciliation
- dispute readiness

The visible unit is not “an impressive agent.” The visible unit is **a completed and accountable service outcome**.

### 8. Keep the layer split crisp

- `MCP` = tool/data entry and façade
- `A2A` / `ACP` = delegation and coordination
- `OpenClaw Market` = offer, lease, proof, settlement, dispute, reconciliation
- chain / wallet / identity = trust anchor and payment rails

Connectivity is not accountability. Coordination is not settlement.

### 9. Digital services first

Mainline v1 stays focused on:

- search
- data enrichment
- model inference
- automation workflows
- code review
- security review

Do not let human-service or `RWA` expansion dilute the first shippable closure.

### 10. Redaction is a product feature

Users and operators should be able to share execution state without exposing:

- raw tokens
- provider endpoints
- real file paths
- sensitive provider credentials

Trust increases when visibility and privacy improve together.

## Strategic shorthand

> **From visible agent behavior, keep the network effect. From accountable execution, keep the product truth.**
